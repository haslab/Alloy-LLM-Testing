Alloy is a formal modelling language that represents a domain using sets, called signatures, and relations, called fields. A concrete instance is a complete valuation of the user-declared signatures and fields, consistent with the model's declarations, imported module constraints, and facts.

Given a natural language requirement, a positive instance satisfies that requirement and a negative instance violates it. Both kinds of instance must satisfy the original model and any earlier requirements that the task says must also hold. A negative instance violates the target requirement while remaining a valid instance of the model and earlier requirements.

Describe each instance as a JSON valuation. A program will translate these valuations into Alloy run commands that fix the complete concrete valuation. Do not formalize the requirement, its negation, or earlier requirements, and do not generate Alloy commands, quantifiers, scopes, expect clauses, or model declarations, facts, predicates, functions, assertions, or check commands.

During evaluation, a correct formalization of the target requirement is enforced as a fact: positive scenarios must remain satisfiable and negative scenarios must become unsatisfiable. Without that target fact, every positive and negative scenario must be satisfiable under the declarations and required background constraints. A classification label does not make a valuation satisfiable or unsatisfiable.

Return one JSON object with exactly two keys: "positive" and "negative". Each key maps to an array of instances of that classification. Return exactly the requested number in each array; if zero are requested for a classification, its array must be []. Each instance is an object with exactly three keys:
- "explanation": a short string explaining why this particular valuation satisfies or violates the current requirement.
- "signatures": an object mapping every user-declared signature name to an array of its atom identifiers, including signatures that are empty.
- "fields": an object mapping every declared field to an array of tuples, including fields that are empty.

Use strings such as "Person1" and "Car1" as atom identifiers. These are names of individual elements, not Alloy expressions. Different identifiers denote different atoms within an instance. A signature's array lists exactly its atoms. A field's array lists exactly its tuples, with each tuple represented by an array of atom identifiers in declaration order. The first element of a field tuple is its owning atom, so an ordinary field from Person to Car is binary and each tuple has two elements. Use [] for an empty signature or field; do not use null, "none", an empty string, or an omitted key to represent emptiness.

Always qualify a field key with its declaring signature, using the exact form "Person <: owns". The <: text is part of the JSON key. Do not write "Person.owns", and do not put Alloy expressions such as "Person1->Car1" inside a value. Valuations use arrays of individual atoms and tuples, not formulas or fragments of Alloy code.

A signature's array fixes its complete population. A top-level domain signature does not extend or form a subset of another signature; abstract top-level signatures count as top-level signatures too. Descendants share their parent's atoms and population bound. The program derives matching exact command scopes from the chosen populations; do not include scopes in the JSON.

If the task supplies a maximum scope n, use at most n atoms in each top-level domain signature, independently. This is not a bound on the total atoms across different top-level signatures. Use fewer atoms, including zero, wherever the model and required background constraints permit. Do not populate a signature merely to reach n. If no maximum is supplied, do not invent one; prefer small, structurally useful scenarios.

Now consider a separate model with a subset and extensions:

sig Person {
    owns : set Car
}
sig Adult in Person {}
abstract sig Car {}
sig Sedan, SUV extends Car {}

Adult may contain any of the Person atoms. Sedan and SUV are disjoint, and together cover the abstract Car signature. Their populations are included in the parent's population bound. For the same requirement, suppose one positive and zero negative instances are requested, with maximum scope 3:

{
    "positive": [
        {
            "explanation": "Every person owns a car; the sedan and SUV cover Car.",
            "signatures": {
                "Person": ["Person1", "Person2", "Person3"],
                "Adult": [],
                "Car": ["Car1", "Car2"],
                "Sedan": ["Car1"],
                "SUV": ["Car2"]
            },
            "fields": {
                "Person <: owns": [
                    ["Person1", "Car1"],
                    ["Person2", "Car2"],
                    ["Person3", "Car2"]
                ]
            }
        }
    ],
    "negative": []
}

Subsignatures reuse their parents' atom identifiers. Car1 in Sedan is the same atom as Car1 in Car; it is not an additional atom. The combined Car population, rather than each extension separately, is bounded by the maximum scope. An inherited field is valued once under its declaring signature: Adult inherits owns, but there is no additional "Adult <: owns" entry.

Finally, consider a separate model with a higher-arity field and an ordering:

open util/ordering[Value]
sig Person {
    owns : Car -> lone Value
}
sig Car {}
sig Value {}

The owns field is ternary: each tuple contains a Person, Car, and Value. For each Person/Car pair, lone permits at most one Value. This does not require every person to own a car or every Value to be used in owns. The util/ordering import requires a nonempty ordered Value population.

For the same requirement, suppose one positive and zero negative instances are requested, with maximum scope 3:

{
    "positive": [
        {
            "explanation": "Every person owns a car at a value; Value3 is unused by owns.",
            "signatures": {
                "Person": ["Person1", "Person2", "Person3"],
                "Car": ["Car1", "Car2"],
                "Value": ["Value1", "Value2", "Value3"]
            },
            "fields": {
                "Person <: owns": [
                    ["Person1", "Car1", "Value1"],
                    ["Person2", "Car2", "Value2"],
                    ["Person3", "Car2", "Value2"]
                ],
                "Value <: next": [
                    ["Value1", "Value2"],
                    ["Value2", "Value3"]
                ]
            }
        }
    ],
    "negative": []
}

The next relation lists only adjacent pairs in a single chain. An ordered signature cannot be empty, even when its values are unused elsewhere. With exactly one ordered atom, its next relation is empty, represented by []. The program derives an exact command scope equal to the chosen population, which need not reach the task's maximum scope.
