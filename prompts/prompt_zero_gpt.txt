Alloy is a formal modelling language that represents a domain using sets, called signatures, and relations, called fields. A concrete instance is a complete valuation of the user-declared signatures and fields, consistent with the model's declarations, imported module constraints, and facts.

Given a natural language requirement, a positive instance satisfies that requirement and a negative instance violates it. Both kinds of instance must satisfy the original model and any earlier requirements that the task says must also hold. A negative instance violates the target requirement while remaining a valid instance of the model and earlier requirements.

Describe each instance as a named Alloy run command. Its body must fix the complete concrete valuation using existentially bound atoms and equality constraints. Do not formalize the requirement, its negation, or earlier requirements, and do not add model declarations, facts, predicates, functions, assertions, or check commands.

Use expect 1 for a positive test and expect 0 for a negative test. These are expected results when a correct formalization of the target requirement is enforced as a fact during evaluation. Without that target fact, every positive and negative scenario must be satisfiable under the declarations and required background constraints. The expect annotation records an expectation; it does not make the run body satisfiable or unsatisfiable.

A command's ordinary scope is an upper bound on a signature, not an exact population. Fix the actual population with a complete signature equality and a matching exact scope. A top-level domain signature does not extend or form a subset of another signature; abstract top-level signatures count as top-level signatures too. Descendants share their parent's atoms and population bound.

If the task supplies a maximum scope n, use at most n atoms in each top-level domain signature, independently. This is not a bound on the total atoms across different top-level signatures. Use fewer atoms, including zero, wherever the model and required background constraints permit. Do not populate a signature merely to reach n. If no maximum is supplied, do not invent one; prefer small, structurally useful scenarios.

Follow these instructions:
- Return exactly the requested positive and negative counts, which may differ. If zero are requested for a classification, emit no commands of that classification. Count the commands before answering.
- Output positive commands first, named PositiveScenario1, PositiveScenario2, and so on, followed by NegativeScenario1, NegativeScenario2, and so on. Use unique names that do not conflict with the supplied model.
- Output only Alloy run commands and Alloy comments, with no Markdown fences or prose outside comments. Appendable commands are required; do not repeat the supplied declarations. Include a short comment stating why each fixed valuation is positive or negative. Include a comment noting that expect labels apply when the target requirement is enforced if it is not already a fact.
- For each nonempty top-level domain signature, bind all its new atoms together in a single some disj declaration. The disj keyword applies to the names in that declaration; separate declarations over the same signature can still bind the same atom. Bind parent atoms once and reuse them for subsets and extensions. For an empty signature, write its equality to none and do not quantify an atom from it. Use existing named singleton or enum atoms directly where appropriate.
- Give every user-declared signature an equality fixing its entire atom set, including abstract parents, extensions, in subsets, and empty signatures. Subsets declared with in may overlap. Sibling extensions declared with extends must be disjoint. An abstract parent's atoms must be covered by its extensions. Respect one, lone, and some signature multiplicities.
- Give every user-declared field an equality fixing its entire tuple set. Use unions of complete tuples with -> between their columns. A field's arity includes its owning signature: a Person field with a Car range is binary; a Person field with a Car -> Value range is ternary. Cardinalities, inclusions, and existential witnesses alone do not fix an instance.
- For empty values, use none for unary signatures, none->none for binary relations, none->none->none for ternary relations, and the corresponding arity for larger relations. An empty value is permitted only when the declarations and required background constraints allow it.
- Respect field multiplicities and arrow multiplicities. For a field with a single signature as its range, omitted multiplicity defaults to one target per owner. A higher-arity field with a bare product range can contain zero or several tuples per owner; apply any multiplicities written on its arrows to the appropriate columns. Do not assume every field contains exactly one tuple per owner.
- Disambiguate overloaded fields with their declaring signature and <:; qualify module names when needed. Value inherited fields under their original declaring signature, rather than inventing additional fields on descendants.
- State matching exact scopes for every top-level domain signature that accepts an explicit scope, including zero populations. Set these scopes to the actual chosen populations, each within any task-supplied maximum. Do not assign separate scopes to subsets or extensions, built-in Int or String, or private module implementation signatures. Respect implicit scopes for singleton and enum signatures. Choose an adequate integer bitwidth if the model uses integers.
- For each util/ordering import, explicitly value its complete binary immediate-successor relation, disambiguating it with the ordered signature and <: and with a module alias when necessary. It must be one chain covering every atom of the ordered signature, without cycles, branches, skipped atoms, or an edge from last to first. An ordered signature cannot be empty. With exactly one ordered atom, its successor relation is none->none. Ordered values may be present even if no other field uses them. Ordering makes that signature's command scope exact, so it must match the chosen population, which can be smaller than a task-supplied maximum. Do not enumerate the module's private implementation signatures or invent independent valuations for first and last.
- Give every irrelevant signature and field a small, explicit legal valuation. It may be empty only if that preserves declaration constraints, module constraints, facts, and all required earlier requirements. Do not use unconstrained or arbitrary values as a substitute for a complete instance.
- Make all scenarios structurally different, including across the two classifications. Renaming atoms, reordering tuples, or changing command names does not create a different scenario. Prefer differences relevant to the requirement, such as empty versus nonempty populations, sharing, connectivity, or cycles where permitted.
- Before answering, check counts, names, complete valuations, atom distinctness, tuple arities, multiplicities, scopes, ordering, background requirements, and each explanation's agreement with its valuation and classification. If the requested scenarios cannot exist within the supplied model and limits, explain the obstacle in Alloy comments rather than supplying invalid scenarios or duplicates.
